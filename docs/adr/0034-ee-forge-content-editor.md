# 0034 — EE FORGE: content editor with JSON project SSOT and one-way vanilla-Lua codegen

**Status:** Accepted.
**Date:** 2026-08-08 (Phase 5 STEP 35).

## Context

Every map, every custom ship, every faction and **all narrative logic**
in EXODUS is hand-written Lua inside chapter files
(`scenarios/chapters/*.lua`): hard-coded coordinates, callsigns assigned
by eye, story beats in a `phases` table, and no preview short of
launching EmptyEpsilon. Five chapters in, the pattern is proven but the
authoring cost per chapter is dominated by transcription, not by design.

`docs/roadmap.md` carries an explicit open question — *"Scenario
authoring tool: visual editor or hand-written Lua? (Decision: defer to
after Phase 4.)"* — and Phase 4 closed with STEP 33 (campaign complete).
The deferral condition is satisfied.

Three facts about EmptyEpsilon EE-2024.12.08 shape every option below.
All three were verified against the pinned install
(`/mnt/c/Win32_EmptyEpsilon_EE-2024.12.08/EmptyEpsilon/`), not assumed:

1. **The API surface is large but self-describing.** 463 methods are
   documented on the classes a content editor would touch
   (`ShipTemplate` 55, `SpaceObject` 50, `ShipTemplateBasedObject` 43,
   `ModelData` 15, `Planet` 11, `Artifact` 11, `ScanProbe` 11,
   `FactionInfo` 9, `WarpJammer` 6, `Zone` 5, …). Too many to
   hand-transcribe into a tool; but `script_reference.html` ships with
   every EE install and is machine-parseable.
2. **EE exposes no enumeration API.** There is no way to ask a running
   EE "what ship templates exist", "what factions exist", "what models
   exist" — only `getFactionInfo(name)` by exact name. Any editor
   library must be built by **parsing the install**:
   `scripts/shiptemplates/*.lua`, `scripts/model_data.lua`,
   `scripts/factionInfo.lua`, `resources/`, `packs/*.pack`.
3. **Load order is fixed** (read from the binary's embedded string
   table): `model_data.lua` → `shipTemplates.lua` → `factionInfo.lua` →
   `scenario_*.lua`. A scenario loads last, so it can create additional
   `ShipTemplate` / `FactionInfo` objects at its own load time.
   `ModelData` is loaded at engine launch; whether a scenario-time
   `ModelData()` registers is an open probe item (§Probe checklist).

The user's requirements, stated up front:

- The editor must produce content usable on **plain EmptyEpsilon**,
  with no EXODUS dependency.
- It must create **maps**, **new ship classes**, **new factions**,
  assign **meshes and textures**, and author the **narrative logic**.
- It must not require modifying the EE install.

## Decision

Build **EE FORGE**: a JSON-document content editor whose only output is
generated vanilla EE Lua.

### 1. `project.json` is the source of truth; Lua is a build artifact

One Zod-validated document per project (`projects/<name>/project.json`)
holds five sections: `factions`, `models`, `templates`, `map`, `logic`.
The editor reads and writes only that document. Generated `.lua` files
carry a `GENERATED BY EE FORGE — DO NOT EDIT` header plus the SHA-256 of
the source document, and are committed alongside it.

**Codegen is one-way. EE FORGE never parses Lua that a human wrote.**
Round-tripping hand-written Lua means writing a Lua parser, preserving
comments and formatting through edits, and merging concurrent changes —
the failure mode that kills tools of this kind. Importing an existing
chapter is a manual port, done once.

This mirrors two patterns the project already runs successfully:
Markdown-as-SSOT for manuals (ADR-0011) and puzzle lookup tables as the
single source of truth for both runtime and printed manuals.

### 2. The verified catalog is the generator

`packages/ee-forge/src/catalog/` parses `script_reference.html` from the
pinned install into `catalog.generated.ts`: every class, every method,
parameter names and types, return type, doc text. A hand-maintained
overlay adds authoring metadata the reference cannot know (which widget
renders a field, which group it belongs to, sensible ranges, whether the
editor exposes it at all).

**The emitters can only emit calls present in the catalog**, and a test
asserts that every `:method(` token in generated Lua resolves to a
catalog entry. Root `CLAUDE.md` §0.3 ("never invent EE Lua API") stops
being a discipline the author must remember and becomes a build
failure — which is the only form of that rule that survives contact
with a 463-method surface.

A version bump of EE is then a re-run of the catalog generator plus a
diff, not an audit.

### 3. Portable bundle output — plus one launch-time file for ship templates

> **CORRECTED 2026-08-09 after probing a live server.** This section
> originally claimed all four content kinds could ride in a scenario-loaded
> bundle and that the EE install would never be touched. **That is false for
> ship templates.** EE refuses them outright — `EmptyEpsilon.log`:
>
> ```
> [ERROR]: ShipTemplate objects can not be created during a scenario.
> ```
>
> Factions and `ModelData` *are* accepted from a scenario; only
> `ShipTemplate` is restricted to the engine's launch-time template phase.
> The decision below is the corrected one.

`forge:build` emits a **portable bundle** to copy into `<EE>/scripts/`:

| File | Contents |
| --- | --- |
| `<name>_content.lua` | factions + models (idempotent; `require`d by the scenario) |
| `<name>_map.lua` | `spawn()` / `spawn_group(name)`, each **returning the created handles** |
| `scenario_<name>.lua` | EE-loadable scenario: `-- Name:` header, `init()`, `update(delta)` |

…and, **only when the project defines ship templates**, one more file that
belongs to a different lifecycle:

| File | Destination | Why |
| --- | --- | --- |
| `<name>_templates.lua` | `<EE>/scripts/shiptemplates/` + one `require` line in `shipTemplates.lua` | Engine restriction: `ShipTemplate()` works only while EE loads templates at launch |

The consequences are stated plainly rather than papered over:

- A project with custom ship classes is **not** a pure drop-in. Installing
  it copies one extra file and adds one line to an EE-owned file, and the
  templates do not exist until **EE is restarted**.
- The tool never mutates an EE file implicitly: `--install` copies files
  (additive) and *prints* the required `require` line; appending it needs
  the explicit `--patch-shiptemplates`. The patch is idempotent and
  preserves the file's line endings.
- A project with no templates keeps the original property: three files,
  copy and play, nothing in the install touched.

Rejected alternative (still rejected, for everything else): patching
`model_data.lua` and `factionInfo.lua` the way this install's own
`galactica_custom.lua` patches `shipTemplates.lua`. It buys visibility in
EE's GM ship-selection menus, but it mutates game files that do not need
mutating — factions and models load fine from a scenario.

### 4. Generated Lua is vanilla; EXODUS integration is caller-side

No `bridge:*`, no `exodus_*` in the emitted map or content files.
`spawn()` returns an array of the objects it created, so an EXODUS
chapter opts in with one line of its own:

```lua
for _, o in ipairs(veil_map.spawn()) do bridge:track(o) end
```

The codegen knows nothing about EXODUS. Narrative **actions** are the
one place where an EXODUS tier exists: a project declaring
`requires: ["exodus"]` unlocks `request_puzzle` / `lore_drop` /
`emit_encrypted_comms` / `complete_chapter` in the action palette.
Without that flag those actions are not offered, and output is provably
vanilla (asserted by a test that greps generated Lua for `bridge:`).

### 5. Logic is data, with two executors

Narrative is not free-text Lua. It is a typed model:

- **beats** — `{ at: seconds, actions: [...] }`, the time-keyed
  scheduler all five chapters already use.
- **rules** — `{ trigger, conditions, actions, once }` for everything
  not time-keyed: player enters an area, group wiped, hull below a
  threshold, variable equals, GM button.
- **variables** — named scenario state.

The same model drives **two executors**: the Lua emitter, and a
TypeScript simulator (`src/logic/simulate.ts`). The simulator lets an
author validate a chapter's flow without launching EE, and doubles as
the test oracle — a parity test asserts the TS execution order matches
the beat/rule order in the generated Lua.

The emitted scheduler is the pattern already canonised in
`docs/authoring/scenarios.md`: `while` (not `if`) so a long tick fires
every skipped beat in order, and `pcall` around each action so one bad
beat does not kill the scenario.

### 6. No RNG in generated Lua

Cluster/belt/field brushes run a seeded PRNG **in TypeScript at
authoring time** and emit literal coordinates. What the editor shows is
byte-for-byte what EE loads, on every launch. `math.random` in a
generated file would make the preview a lie.

### 7. Topology

```
packages/shared/src/schemas/ee-project.ts   EEProjectSchema  (SSOT + wire)
packages/shared/src/schemas/ee-library.ts   EELibrarySchema  (install index)
packages/ee-forge/                          pure TS: zod + @exodus/shared only
packages/bridge/src/forge/routes.ts         HTTP surface for the editor
packages/web-forge/                         Vite + React editor, port 5176
projects/<name>/project.json                committed SSOT
projects/<name>/build/*.lua                 committed artifacts
```

Schemas live in `@exodus/shared` because the editor ↔ bridge traffic is
bridge↔web traffic (root §0.3). Catalog, scanner, simulator and
emitters live in `packages/ee-forge`, which depends on nothing but
`zod` and `@exodus/shared` — so a future standalone distribution
(the tool usable without the EXODUS monorepo) is a packaging exercise,
not a rewrite.

## Probe checklist — results (probed 2026-08-09 against a live EE-2024.12.08)

Seven items the design leans on that stock EE scripts do not
demonstrate. Per root §0.3 each is verified against a live server before
being relied upon. Full detail in `docs/ee-api-reference.md` §15.2.

| # | Item | Outcome |
| --- | --- | --- |
| 1 | `setScenario(script, variation)` — documented, but `docs/ee-api-reference.md` §9.1 declared it absent and [ADR-0030](./0030-container-scenario-and-chapter-modules.md) was built on that premise | **CLOSED: it works.** `pcall(setScenario, "scenario_forge_demo.lua")` returned ok, and `EmptyEpsilon.log` shows `Configuring settings for scenario …` / `Load script: scenario_forge_demo.lua`. **§9.1's claim was wrong.** ADR-0030's container scenario and ADR-0021's operator-driven resume are now *choices* rather than the only option — revisiting either is out of scope here and needs its own ADR. |
| 2 | `getFactionInfo("<unknown>")` — nil or error? | **CLOSED: returns `nil`, does not raise.** The content emitter dropped its defensive `pcall`; faction creation is a plain idempotent guard. |
| 3 | `ShipTemplate()` at scenario load | **CLOSED: refused.** `[ERROR]: ShipTemplate objects can not be created during a scenario.` Also nil over `/exec.lua`. This invalidated the original §3 and forced the launch-time template file — the single most consequential probe result. |
| 4 | `ModelData()` outside launch-time `model_data.lua` | **CLOSED, with a load-order catch.** Registration is accepted both over `/exec.lua` and from a scenario (a redefinition logs `Duplicate modeldata definition: <name>`). But a *template* resolves `setModel()` during `shipTemplates.lua`, before any scenario — so a scenario-registered model yields `Failed to find model data: <name>` and a silent fallback mesh. Models therefore ship in the launch-time file alongside the templates. Verified after the fix: the model registers and binds (absent from EE's *"not used by any ship template"* list, no `Failed to find model data`). |
| 5 | `Zone():setPoints(...)` + `isInside` | **CLOSED, and the upstream doc is wrong.** The reference says zones cannot be created over `/exec.lua`; they can. `setPoints` takes flat x,y pairs, `getLabel()` reads back, and `isInside(player)` answers correctly — so area triggers use EE's own containment, not our geometry. |
| 6 | Comms hooks on a spawned ship | **CLOSED.** `setCommsScript`, `setCommsFunction` and `openCommsTo` all exist on a spawned `CpuShip` (defined on `SpaceObject`) and all three are in the generated catalog. Dialogue authoring (STEP 37) has a real surface to target. |
| 7 | `setCallSign` on the non-ship types | **CLOSED.** Round-trips on all ten: Asteroid, Mine, Planet, Nebula, BlackHole, WormHole, SupplyDrop, Artifact, ScanProbe, WarpJammer. The `ScriptStorage` fallback in `docs/authoring/naming-convention.md` is unnecessary. |

**GM callbacks must close over nothing but `_ENV`.** `addGMFunction`
converts through `convert<ScriptSimpleCallback>`, which reads upvalue 1 and
requires a table. The first version of the logic emitter wrapped GM bodies
in a local `run()` helper, so the closure captured `run` as upvalue 1 and
`init()` died on the first button with *"Upvalue 1 of function is not a
table"*. The emitted runtime is now two prefixed globals (`<id>_rt`,
`<id>_state`) addressed by full name everywhere, which makes the bug
structurally impossible to reintroduce. Verified live: the scenario now
loads with zero errors in `EmptyEpsilon.log`.

Additional findings from the same session, recorded in the reference:

- **Every `/exec.lua` request runs in a fresh Lua state.** A global set by
  one request is gone by the next, so a `require`d module must be
  re-required inside each call that uses it. This shapes STEP 40's live
  push: it can spawn objects, but it cannot hold state between calls.
- `addGMFunction` over HTTP fails with a `ScriptSimpleCallback`
  conversion error, confirming the reference's #1807 note.
- The generated map module was exercised against the live server: the
  demo's 11-object `core` group spawned with every authored property
  intact (callsigns, station template + hull, planet radii, asteroid
  sizes, zone label), then was removed cleanly.

## Alternatives considered

- **Hand-written Lua forever (status quo).** Zero tooling cost, and the
  five shipped chapters prove it works. Rejected because the marginal
  cost per chapter is transcription, the callsign convention in
  `docs/authoring/naming-convention.md` has no enforcement point, and
  nothing catches an invented API call until EE errors at runtime.
- **Round-trip editor over existing Lua.** Would let the editor open
  `chapter_05_serpents_coil.lua` directly. Rejected: needs a Lua
  parser, loses comments and authorial structure on write, and creates
  a merge problem between the editor's view and hand edits.
- **Patch the EE install** (see §3). Rejected as the default; the
  visibility gain in EE's menus does not pay for mutating game files
  and losing portability.
- **Blueprint-style node graph for narrative.** Visually appealing and
  the obvious "graphical logic" answer. Rejected for v1: 3-4× the build
  cost, and for the 10-beat, mostly-linear chapters this project
  actually writes, a timeline plus a WHEN/IF/THEN table is easier to
  read than a canvas of wires. A generated read-only mermaid flowchart
  gives the visual overview at ~1% of the cost. The graph can later be
  added as another view over the same model, with no data migration.
- **Editor as a route inside `web-cockpit`.** Rejected for the same
  reason ADR-0022 kept the codex standalone: the cockpit is a
  player-facing surface with an always-on aesthetic; the forge is an
  authoring tool with a different layout language and lifecycle.

## Consequences

- **A new package boundary.** `packages/ee-forge` must stay free of
  bridge/web dependencies for the standalone path to remain open. The
  bridge imports it, never the reverse.
- **Generated files are committed.** The repo gains `projects/*/build/*.lua`.
  They are artifacts, but committing them keeps a playtest reproducible
  from a checkout without running the toolchain, matching how
  `assets/manifest.json` is handled.
- **The catalog pins an EE version.** `catalog.generated.ts` is valid for
  EE-2024.12.08. Upgrading EE means re-running `ee:catalog` and reading
  the diff — which is a feature: the diff *is* the upgrade impact report.
- **The callsign convention finally has an enforcement point.** Auto-
  assignment in the editor is what makes viewer clustering, HUD counts,
  GM filtering and per-group persistence real instead of aspirational.
- **Narrative authoring gains a test surface.** Beats and rules become
  data, so a chapter's flow can be unit-tested (simulator) before it is
  ever loaded into EE.
- **Two sources of truth exist during migration.** Chapters 01–05 stay
  hand-written Lua; new content uses the forge. Migrating the old
  chapters is optional and explicitly not part of STEP 35.
